## 1. 代码理解与接口

### 1.1 原始程序 `baseline.cpp` 的职责划分

原始程序把所有职责堆在 `main` 里，先识别出各部分：

| 职责 | 位置 | 说明 |
|---|---|---|
| 参数解析 | `main` 开头的 `for` 循环 | 解析 `--count` / `--pattern` / `--repeats` 等 |
| 输入生成/加载 | `generate(...)` 或 `load(...)` | **在计时范围之外** |
| **核心计算** | `main` 中的 `for (i...)` 循环 | 稳定筛选，**这是唯一被计时的部分** |
| 参考校验 | `reference_filter(...)` + 逐条 `equal_record` | 计时之外 |
| 计时 | `steady_clock` 包住核心循环 | 预热 1 次不计入，之后测 `repeats` 次 |
| 输出 | `save(...)` | 计时之外 |

**计时边界**（很关键）：只包含核心筛选循环（含全部输出写入），
**不包含**数据生成、参考实现、校验、打印和文件写入。

### 1.2 抽取的接口

```cpp
std::size_t filter_records(const Record* input, std::size_t count,
                           Record* output, const Query& query);
```

**约定**（严格按题目要求）：

- `input` / `output` 不重叠；`output` 容量至少 `count`
- `count == 0` 时允许空指针
- 返回命中条数；**有效结果只是 `output` 的前 `matched` 个**
- 函数内不打印、不读文件、不产生测试数据、不调用参考实现

**保持的语义**：

- **稳定**：命中记录之间的相对顺序与输入一致
- **保留全部字段**：整条 `Record` 拷贝，不是只拷部分字段
- **不去重**：重复记录照样输出
- 三个筛选条件与顺序均未改变

### 1.3 重构的验证

重构后跑组织者提供的公开测试：

```

$ python3 src/test_public.py ./refactored
.......
Ran 7 tests in 0.199s
OK
```

**7 项全过** —— 证明重构只搬动了代码位置，没有改变行为。

### 2.2 ⚠️ 测量环境的坑：CPU 电源模式

**第一次测量时数据极不稳定**：同一份代码、同一份数据，中位数在 **0.35 ms ~ 0.69 ms** 之间跳动（约 2 倍），
且呈现"整段快/整段慢"的切换，而不是平滑变化。

排查过程：

| 步骤 | 命令 | 结果 |
|---|---|---|
| ① 排除外部干扰 | `top -bn1 \| head -15` | CPU **99.4% 空闲**，无进程抢占 |
| ② 看电源策略 | `cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor` | **`powersave`** |
| ③ 看实际频率 | `grep MHz /proc/cpuinfo` | 空闲核 800 MHz，负载核可跳到 4.9 GHz |

**结论**：`powersave` 是按需调频，空闲时降频到 800 MHz，一有负载才拉高。
短小的基准测试（0.3 ms）正好落在"频率还没拉起来"的窗口里，所以结果随机的快慢。

**对策**（没有修改系统设置，而是改进测量方法）：

1. **交替测量**：A/B/A/B 轮流跑，而不是"连测 5 次 A 再连测 5 次 B"
2. **增大 repeats**：从 5 次提高到 10~20 次，取中位数
3. 结论：**两种实现的对比在同一波动下进行，相对关系仍然成立**

> **诚实说明**：本报告所有数据都是**本地实体机**在 `powersave` 调频下的结果。
> 题目明确指出"本地或 WSL 2 的性能数据不能替代正式服务器结果"，
> 因此本报告的绝对数值仅供参考，**结论以相对趋势为准**。

## 3. 热点、假设与选择

### 3.1 热点证据

**观测**：把命中分布从 `random` 换成 `blocks`（**命中数量几乎相同**，只改分布），
速度明显变化：

| N | random 中位数 | blocks 中位数 | blocks 快 |
|---|---|---|---|
| 100,000 | 0.346 ms | 0.239 ms | **1.45×** |
| 1,000,000 | 3.808 ms | 3.017 ms | **1.26×** |

**两种分布的差别只有一个**：

- `random`：命中/不命中**随机交替** → 筛选条件的分支**不可预测**
- `blocks`：每 10000 条里前 5000 条命中 → **连续同方向**，分支**高度可预测**

**证据覆盖范围**：程序内置计时只覆盖核心筛选循环，**不含**数据生成、校验、打印，
因此这个差异**来自核心区域**，不是整个进程的干扰。

### 3.2 假设

> **假设 H1**：核心筛选的热点是**分支预测失败**。
> 筛选条件用短路的 `&&` 串联，`random` 分布下判断结果随机，
> 分支预测器频繁猜错，每次猜错要清空流水线（约 10~20 周期）。
>
> **可推翻条件**：如果消除分支后性能**没有改善**，则 H1 不成立。

### 3.3 两个候选方向

| 候选 | 做法 | 预期改善 | 额外成本 | 是否实现 |
|---|---|---|---|---|
| **A. 无分支化（branchless）** | 用 `&` 代替 `&&`，把判断结果算成 0/1；无条件写入 + 指针按命中数前进 | 消除分支预测失败 | 不命中时会多写一次内存 | ✅ 实现了 |
| **B. 多线程 + 前缀和** | 输入切连续块，第一遍各线程计数，排他前缀和算出各块输出起点，第二遍各线程写自己区间 | 利用多核并行 | 输入扫两遍、每次调用创建线程、临时分配 | ✅ 实现了 |

**为什么选这两个**：A 直接针对 H1；B 是题目分层提示中指出的方向，
且"稳定顺序"与"无写冲突"在 B 里是需要专门解决的问题（见第 4 节）。

## 4. 实现与正确性

### 4.1 候选 A：无分支筛选

```cpp
const bool hit = (q.begin <= r.timestamp) & (r.timestamp < q.end) &
                 (r.latency_us >= q.min_latency_us) &
                 ((r.flags & q.required_flags) == q.required_flags);
const std::size_t bit = hit ? 1u : 0u;
output[matched] = r;   // 无条件写
matched += bit;        // 只有命中才前进
```

**正确性论证**：有效结果只是 `output` 的前 `matched` 条。
不命中时 `bit = 0`，会把同一条未命中记录重复写到同一个位置，
**该位置不在有效结果范围内**，下一次命中会把它覆盖掉，因此输出正确。

**关键点**：用 `&` 而非 `&&` —— 按位与**不短路**，不产生额外分支。

### 4.2 候选 B：多线程 + 两遍扫描 + 排他前缀和

```
第一遍（并行）：各线程只【计数】自己块内的命中数，不写 output
        ↓
排他前缀和（串行）：offsets[t] = 前 t 块的命中总数 = 第 t 块的输出起点
        ↓
第二遍（并行）：各线程只写自己那段连续区间 [offsets[t], offsets[t]+counts[t])
```

**稳定性保证**：输入按**连续块**切分，块内保持原顺序；
每块写进自己那段连续区间；块间按前缀和顺序排列 → **整体顺序 = 输入顺序**。
**无写冲突**：各线程的写入区间互不重叠。

### 4.3 ⚠️ 踩到的 bug：无条件写在并行下会越界（数据竞争）

**第一版实现把 A 的"无条件写"直接搬到 B 里**，结果公开测试报错：

```
error: validation: wrong record/order at 18870
```

**原因**：A 的"不命中时多写一格"在**串行**下无害（下一格会被覆盖），
但在**并行**下，那一格正好是**下一个线程的第一个写入位置**：

```
线程 t 的区间: [offsets[t], offsets[t]+counts[t])
                                                  ↑ 不命中时写到这里
                                    线程 t+1 从这里开始写 ← 两个线程抢同一格
```

→ **数据竞争**，结果顺序错乱。

**修复**：并行版的第二遍改用 `if (hit) output[pos++] = r;`——
只写命中的记录，绝不越过本块区间。

**这个 bug 说明**：**两个优化方向存在冲突**。
无分支技巧依赖"无条件写"，而并行要求"严格区间隔离"，二者不能简单叠加。

### 4.4 正确性验证

**公开测试**（组织者提供，7 项）：

| 版本 | 结果 |
|---|---|
| `refactored` | `Ran 7 tests ... OK` |
| `branchless` | `Ran 7 tests ... OK` |
| `parallel` | `Ran 7 tests ... OK` |

**新增边界测试**（`src/test_boundary.py`，24 项 × 3 版本）：

| # | 用例 | 为什么必要 |
|---|---|---|
| 1 | `count=0`（空输入） | 循环不执行，空指针路径 |
| 2 | `count=1` | 最小规模 |
| 3 | `count=3`（**少于线程数**） | 并行会分 8 块，块数 > 数据条数 |
| 4 | `hit-percent=100`（全命中） | `output` 是否会写超 |
| 5 | `hit-percent=0`（全不命中） | 是否会写不该写的位置 |
| 6 | `begin == end`（空查询区间） | 一条都不该命中 |
| 7 | `count=100003`（**除不尽**） | 并行最后一块偏小（**针对 4.3 的 bug 设计**） |
| 8 | blocks + 全命中 | 另一种 pattern |
| 9 | 极宽查询区间（三个条件全放宽） | 走不同条件分支 |

**结果**：

```
refactored : 通过 24 项，失败 0 项
branchless : 通过 24 项，失败 0 项
parallel   : 通过 24 项，失败 0 项
```

**比较的内容**：数量（`matched`）、字段与顺序（程序内置的 `equal_record` 逐条比对）、
以及每次运行的 `check=PASS`。**优化前后使用完全相同的输入、查询和计时范围。**

## 5. 性能与适用条件

### 5.1 主对比表

同一轮测量、相同输入与查询（`--pattern random --hit-percent 50 --repeats 10`）：

| 实现 | N | 命中率 | 线程 | 中位数 (ms) | Mrec/s | 相对基线 |
|---|---|---|---|---|---|---|
| refactored（基线） | 100,000 | 50.156% | 1 | **0.3125** | 320.0 | 1.00× |
| branchless（A） | 100,000 | 50.156% | 1 | **0.1661** | 602.2 | **1.88×** |
| parallel（B） | 100,000 | 50.156% | ≤8 | **0.4270** | 234.2 | **0.73×（退化）** |
| refactored | 1,000,000 | 50.013% | 1 | **3.3745** | 296.3 | 1.00× |
| branchless | 1,000,000 | 50.013% | 1 | **1.7161** | 582.7 | **1.97×** |
| parallel | 1,000,000 | 50.013% | ≤8 | **1.8331** | 545.5 | **1.84×** |
| refactored | 10,000,000 | 50.001% | 1 | **36.268** | 275.7 | 1.00× |
| branchless | 10,000,000 | 50.001% | 1 | **18.015** | 555.1 | **2.01×** |
| parallel | 10,000,000 | 50.001% | ≤8 | **16.214** | 616.7 | **2.24×** |

**原始样本**：每组 10 次原始耗时保存在 `results/cmp-*.txt`。

### 5.2 解释：提升、退化与"分界线"

**① 候选 A（无分支）：在所有规模下稳定提升约 1.9~2.0 倍**

假设 H1 得到支持。但**注意一个意外结果**：
`blocks` 分布本来分支就容易预测，**但它的 branchless 版本同样大幅变快**
（100k：0.165 ms vs 基线 0.239 ms）。

**这说明收益不只来自"减少分支预测失败"**，还来自：

- **指令数减少**：`&` 一行算完四个条件，比短路的 `&&` 少很多跳转指令
- **流水线连续**：没有跳转，CPU 可以连续预执行

**所以 H1 只解释了一部分收益，实际原因是"分支预测失败减少 + 指令数减少"共同作用。**
（这属于"实测修正了原假设"。）

**② 候选 B（并行）：小规模退化，大规模才见效**

| N | branchless | parallel | 判断 |
|---|---|---|---|
| 100,000 | 0.166 ms | 0.427 ms | **并行慢 2.6 倍** ❌ |
| 1,000,000 | 1.716 ms | 1.833 ms | 差异 7%，**在噪声范围内** |
| 10,000,000 | 18.015 ms | 16.214 ms | **并行快 1.11 倍** ✅ |

**小规模退化的原因**：10 万条只需 0.17 ms，而**创建 8 个线程本身的固定开销**就有几十微秒，
**线程开销 > 省下的计算时间**。

**大规模收益有限的原因**：

- 输入要**扫两遍**（计数 + 写出）
- 1000 万条 × 24 字节 = **240 MB**，扫两遍 = **480 MB**
- `480 MB ÷ 16.2 ms ≈ 29.6 GB/s` —— **这已经接近这台机器单线程可用的内存带宽量级**

因此这个程序在 1000 万条规模下**已经开始受内存带宽限制**，
增加线程数也无法突破带宽上限，所以只快 1.11 倍而不是 8 倍。

**③ 为什么两个候选都有收益、却不能简单叠加**

见 4.3：并行版必须放弃"无条件写"，分支又回来了。
所以 `parallel` 的收益来自并行，**但它内部的有分支写法抵消了一部分**，
这也是它相对 `branchless` 只在 1000 万条时才反超的原因。

### 5.3 适用的调用场景

| 实现 | 推荐场景 | 不推荐场景 |
|---|---|---|
| **branchless** | **任何规模都推荐**；改动小、无额外内存、稳定 2 倍 | —— |
| **parallel** | 超大规模（≥1000 万条）、且**重复查询**（可复用输入时摊销线程开销） | 小批量（≤100 万条）；一次性短查询 |

**若把初始化（线程池 / 数据转换）放到计时之外**：本实现没有这样做，
`counts` / `offsets` 的分配和线程创建**全部计入计时**，因此数据是保守的。

**是否受缓存影响**：小规模数据能放进缓存，大规模（10M = 240 MB）必然溢出到内存，
这也是大规模下并行收益受限于带宽的原因。

## 附录 B：构建与运行

```bash
# 编译（三个版本用完全相同的编译参数）
g++ -O2 -std=c++17 -Isrc -o refactored src/refactored.cpp
g++ -O2 -std=c++17 -Isrc -o branchless src/branchless.cpp
g++ -O2 -std=c++17 -pthread -Isrc -o parallel src/parallel.cpp

# 公开测试
python3 src/test_public.py ./refactored
python3 src/test_public.py ./branchless
python3 src/test_public.py ./parallel

# 边界测试
python3 src/test_boundary.py ./refactored
python3 src/test_boundary.py ./branchless
python3 src/test_boundary.py ./parallel

# 性能对比
for n in 100000 1000000 10000000; do
  for v in refactored branchless parallel; do
    ./$v --count $n --pattern random --hit-percent 50 --repeats 10
  done
done
```

## 附录 C：不确定与未验证的部分

1. **绝对数值不能与服务器结果比较**。题目明确说明本地性能数据不能替代正式 runner 结果，
   且本机 CPU 处于 `powersave` 按需调频状态。
2. **候选 B 的线程上限固定为 8**（`hardware_concurrency()` 上限 8），
   未测试更多线程数是否更好；也未测试不同块大小的影响。
3. **`-O3`、SIMD、数据布局转换等方向未实测**，仅在候选分析中讨论。
4. **未做 perf 硬件计数器采集**。`perf stat` 的统计覆盖整个进程
   （含数据生成、FP64 参考、校验），不能直接除以核心循环耗时。
5. **`blocks` 分布在 branchless 版本下的表现存在一次异常**
   （branchless-blocks-100k = 0.165 ms 反而慢于 branchless-random-100k = 0.099 ms），
   与"blocks 分支更可预测"的直觉相反，**仅测一轮，未复现确认**，需要进一步测量。
